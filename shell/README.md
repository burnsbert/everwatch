# Everwatch.app shell — maintainer notes

A thin AppKit wrapper around the Python backend (see `docs/DESIGN.md` §3.1).
It's built with `swiftc` directly. SwiftPM is broken on the current Command
Line Tools (§5.4).

```
shell/
  Sources/Core/   Foundation-only logic, fully unit-tested
  Sources/App/    AppKit / WebKit / UserNotifications / Carbon glue (compiled, never run in tests,
                  except SilentResponders.swift (see "Unhandled keys never beep") and
                  StatusGlyph.swift (a pure drawing helper, called directly by its tests))
  Tests/          Swift Testing suites + Runner.swift (entry point)
  Info.plist      bundle id io.github.burnsbert.everwatch, macOS 13+, LSUIElement=false
  AppIcon.icns    generated by scripts/make_icon.sh (CoreGraphics + iconutil, headless)
```

## Build and test

| Command | Result |
|---|---|
| `scripts/build_app.sh` | `build/Everwatch.app`: universal (arm64 + x86_64), `-O`, ad-hoc signed |
| `scripts/build_app.sh --dev` | Native arch only, debug build (faster) |
| `scripts/build_app.sh --tests && build/shell-tests` | Swift Testing over `Sources/Core`, `Sources/App/SilentResponders.swift`, and `Sources/App/StatusGlyph.swift`, plus a compile check of `Sources/App` (`make test-swift`) |
| `scripts/build_app.sh --coverage` | Instrumented test run, then an `llvm-cov report` for `Sources/Core` |
| `scripts/make_icon.sh` | Regenerates `shell/AppIcon.icns` (`build_app.sh` runs it if the file is missing) |

The x86_64 link prints
`ignoring file …/libswiftCompatibilityPacks.a: fat file missing arch 'x86_64'`.
This is expected (§4.3).

The test runner uses `Testing.__swiftPMEntryPoint`, which is underscored SPI.
If a toolchain update removes it, `build_app.sh --tests` stops with a clear
message, and `Tests/Runner.swift` needs updating.

Tests never play sound. Core has no audible code at all, the cue player is a
recording fake, and `Runner.swift` sets `EVERWATCH_NO_SOUND=1` before any test
runs. Tag tests that cover a parity row with a `// # parity: P-66` comment on
the line above `@Test` (`scripts/check_parity.py`).

## Unhandled keys never beep

WKWebView sends every key the page doesn't `preventDefault()` back up the
responder chain (WebKit `WebViewImpl::doneWithKeyEvent`). At the end of the
chain, AppKit's default `-[NSResponder noResponderFor:]` plays the alert
sound for `keyDown:`. Everwatch silences that in two layers, both routed
through `UnhandledEventPolicy.drop` (`Sources/Core/UnhandledEventPolicy.swift`),
which records the event and never beeps:

1. **Subclasses (primary, statically checkable).** Every window or panel
   that hosts a web view is a `SilentWindow` or `SilentPanel`, and the app
   object is a `SilentApplication` (`Sources/App/SilentResponders.swift`).
   Each overrides `noResponder(for:)` and never calls super.
   `scripts/lint_nosound.py` rejects a bare `NSWindow(` / `NSPanel(`, other
   direct subclasses of those or of `NSApplication`, and
   `NSApplication.shared` in `shell/Sources`, plus `super.noResponder(` in
   any Swift file.
2. **Process-wide.** `main.swift` calls
   `SilentResponders.installProcessWide()` before anything else. It swaps
   NSResponder's own `noResponderFor:` implementation for the silent one
   (`SilentMethodPatch`: `class_replaceMethod`, idempotent, the original is
   never called). This covers windows Everwatch doesn't create, such as the
   standard About panel.

Key equivalents, menus, text input and IME, Tab, and Esc are unaffected.
They all run before an event can fall off the end of the chain.

`build/shell-tests` compiles `SilentResponders.swift`. It inspects those
classes without creating them, and it installs the process-wide layer in
the test process, which has no windows or events. The self-test's
`silent_responder_chain` check inspects the live chains and IMPs. It calls
an override directly only after proving by IMP identity that the override
is what will run, so AppKit's original is never invoked.

## Runtime resolution

| Variable | Effect |
|---|---|
| `EVERWATCH_HOME` | Data dir (default `~/Library/Application Support/Everwatch`) |
| `EVERWATCH_RUNTIME` | Directory put on `PYTHONPATH`; it must contain `everwatch/__main__.py`. Default `$EVERWATCH_HOME/runtime/current`. For development, point it at the repo root. |
| `EVERWATCH_PYTHON` | Interpreter to try first |
| `EVERWATCH_NO_SOUND` | Any non-empty value hard-disables the attention sound |

Python search order (`PythonLocator`): `EVERWATCH_PYTHON`, then
`$EVERWATCH_HOME/venv/bin/python3`, `/opt/homebrew/bin/python3`,
`/usr/local/bin/python3`, python.org's framework, and finally
`/usr/bin/python3`. The last one is used only if `xcode-select -p` reports a
developer dir that contains `usr/bin/python3`, because running the stub
without the CLT opens the install dialog. The minimum version is 3.9.

The backend is spawned as `python3 -m everwatch serve --port 0 --parent-pipe`
with cwd = the runtime dir, and with `EVERWATCH_TOKEN`, `EVERWATCH_HOME`,
`EVERWATCH_SHELL=1`, and `PYTHONUNBUFFERED=1` set. The shell waits up to 20 s
for `EVERWATCH_READY <port>` on stdout. It holds the backend's stdin open
(EOF means exit) and restarts it after 1 s, 2 s, then 4 s. More than 3
crashes in 60 s shows a local error page with a "Try again" link
(`everwatch://retry`).

**Requested restarts (exit code 75) skip the backoff.** A backend that
exits with status **75** (`sysexits.h EX_TEMPFAIL`,
`everwatch.cli.EX_TEMPFAIL` in Python, `BackendExitCode.tempFail` in
`Sources/Core/BackendConfig.swift`) is asking to be restarted right away,
not reporting a crash — currently only the tab-colors installer
(`POST /api/colors/install`) uses this, once it finishes successfully and
needs the freshly installed `iterm2` package on the venv's python at the
next spawn. `RestartPolicy.decide(exitStatus:at:)` restarts on this
immediately and never adds it to the crash window, so it can never itself
trigger, or count toward, the "more than 3 crashes in 60 s" error page.
Every other exit status (including a normal 0 from a parent-pipe
EOF/SIGTERM) still goes through the 1 s/2 s/4 s backoff exactly as
before.

## Web ↔ shell contract

**Document-start user script** (main frame only; the token is never put in a URL):

```js
window.everwatchNative = {
  shell: true, token: "<43-char base64url>", shellVersion: "0.1.0",
  queue: [],                    // messages dispatched before the page installed its handler
  dispatch(m) { queue.push(m) } // the page's bridge.mjs should replace this and drain `queue`
}
```

**Web → shell** (`window.webkit.messageHandlers.everwatch.postMessage(obj)`).
These are accepted only from `http://127.0.0.1:<port>` / `localhost:<port>`
main-frame documents: `appearance{theme: system|dark|light}`, `openCompact`,
`openSettings`, `requestNotifications`,
`openSystemSettings{pane: automation|notifications}`,
`setHotkeys{show, next}` (an empty string disables one), and `ready`.
Nothing makes sound.

**Shell → web** (`everwatchNative.dispatch(obj)`):
- `notificationClicked{uid}`
- `focus{key: bool}`
- `openSettings`: sent when Settings is chosen from the menu bar or app menu,
  or when the compact panel asks for it. This one is an addition to §3.5.
- `nativeStatus{automation, notifications, hotkeys}`, where:
  - `automation`: `granted | not_determined | denied | not_running | unknown`
    (from `AEDeterminePermissionToAutomateTarget(…, askUserIfNeeded: false)`)
  - `notifications`: `authorized | denied | not_determined | unknown`
  - `hotkeys`: `{show, next}`, each `ok | disabled | invalid | conflict | error`

`nativeStatus` is sent after `ready`, `requestNotifications`, and
`setHotkeys`. It is also re-probed and re-sent whenever the backend's
`iterm.status` changes (seen over the shell's own SSE), so `automation` is
never a stale snapshot from before the user answered the prompt. The web
treats `automation` as a fill-in only: the backend's own osascript result
(`ok`/`error`) always wins (`everwatch/web/js/lib/diagnostics_ui.mjs`).

The shell's own SSE client consumes `hello`, `state`, `transition`, `notify`,
`quota_prompt`, and `ping`, and ignores the rest.

## Manual smoke test (maintainer, on a real Mac; not CI)

These can't be automated headlessly. Run them after shell changes:

1. First launch with no python3 ≥ 3.9 shows the error page with copyable
   commands. "Try again" works after installing Python.
2. With the runtime installed, the window loads the UI, the menu bar shows the
   dim eye, and the Dock icon appears.
3. The first poll shows the TCC prompt **"Everwatch" wants to control
   "iTerm2"** with the `NSAppleEventsUsageDescription` text. Confirm it names
   Everwatch and not Python (§8 risk).
4. After "Don't Allow", `nativeStatus.automation` becomes `denied`. After
   granting, it becomes `granted`.
5. "Allow notifications" asks for alerts and badges only. A notification
   arrives silently while iTerm2 is frontmost, doesn't appear while the
   Everwatch window is key, and clicking it focuses that iTerm2 session.
6. The menu bar shows amber `◉ N` when sessions are waiting. The menu lists
   them longest-first, and clicking one goes there.
7. ⌥⌘E brings Everwatch forward. ⌥⌘J jumps to the longest-waiting session
   without showing Everwatch.
8. ⌘\ toggles the compact floating panel. Clicking it doesn't take focus
   from iTerm2, and its position persists across launches.
9. ⌘W hides the window and the menu bar keeps updating. The Dock icon
   reopens the window, and its frame persists.
10. Theme changes in Settings switch the title bar appearance.
11. The sound pref is off by default. With it on and `EVERWATCH_NO_SOUND`
    unset, a transition to waiting plays one system cue. Launched with
    `EVERWATCH_NO_SOUND=1`, it's silent.
12. Quitting Everwatch leaves no `everwatch serve` process behind
    (`pgrep -fl "everwatch serve"`).

Rebuilding changes the ad-hoc cdhash, so macOS asks for Automation again
(§4.3).
